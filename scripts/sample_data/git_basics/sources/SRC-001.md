# What a commit really records

A Git commit is a labelled checkpoint of your whole project. This note explains what goes into that checkpoint and how the staging area lets you choose.

## A commit is a snapshot

A commit points to a complete listing of the project's tracked files as they were at that moment. It also stores an author and a committer, a timestamp for each, a message, and a pointer to the commit that came before it. The first commit in a repository has no parent.

Git names each commit with a long hexadecimal ID computed from the commit's contents: the tree, the parent, the author and committer with their timestamps and time-zone offsets, and the message. Change any of them and the ID changes. The short IDs in `git log --oneline` are the start of the full ID.

Many newcomers believe that a commit stores only the lines you changed. It does not. The commit refers to the whole set of tracked files, and a file you did not touch refers to the same stored content as in the previous commit, so that content is stored once. When you ask for a difference, `git diff` works it out on the spot by comparing two snapshots. Git may compress similar file versions inside its packed storage, but that internal optimization does not change what a commit means.

## The staging area sits in between

Your working folder is where you edit. The staging area, also called the index, is where you assemble the next commit. `git add` copies the current content of a file into the staging area, and `git commit` records what is staged, not what happens to be on disk.

A common mistake is to run `git add notes.txt`, keep typing in that file, and then assume the commit contains the later edits. It contains the version you staged. Before you commit, `git status` lists the file twice: once as staged, once as changed but not staged. After the commit it lists the file once, as changed but not staged. Stage the file again to include the newer edits.

A common mistake is also to expect `git commit -a` to pick up brand-new files. It stages modifications and deletions of files that Git already tracks, but a new file stays untracked until you run `git add` on it. Git also tracks files, not folders, so an empty folder does not appear in a commit.

## Reading what you have

- `git status` summarizes what is staged, modified or untracked.
- `git diff` compares your working folder with the staging area.
- `git diff --staged` compares the staging area with the last commit.
- `git log --oneline` lists commits from the newest backwards, one line each.

Running these before a commit shows you what you are about to record.
