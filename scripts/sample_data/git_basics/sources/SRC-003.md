# Conflicts and undo: a field guide

Two situations can catch a new team member off guard: a merge that stops halfway, and the urge to take something back.

## When a merge stops

A conflict happens when both branches changed the same lines differently or changed neighboring lines, or when one branch deleted a file that the other edited. Changes to lines that are not next to each other usually merge automatically.

When Git stops on a file both branches edited, `git status` lists it under "Unmerged paths" as "both modified", and the file contains markers:

- `<<<<<<< HEAD` opens the block. The lines after it are the version on your current branch.
- `=======` separates the two versions.
- `>>>>>>> feature` closes the block. The lines before it are the other branch's version, labelled with the branch you merged.

To resolve it, edit the file into the text you want, delete the marker lines, run `git add`, then `git commit` (or `git merge --continue`, Git 2.19 or later). To back out, run `git merge --abort`; if you began from a clean working folder, your branch returns to how it was.

A common mistake is to stage a file that still contains markers to clear the unmerged status. By default, Git accepts that commit. `git diff --check` reports each "leftover conflict marker" before staging; afterwards use `git diff --cached --check`.

## Taking things back

| Command | Effect |
|---|---|
| `git restore file` | Replaces the working copy with the staged (or last committed) version |
| `git restore --staged file` | Unstages the file and keeps your edits |
| `git revert commit` | Adds a new commit that cancels an earlier one |
| `git reset` | Moves the current branch to another commit (commit form) |

`git restore` needs Git 2.23 or later.

`git reset` has three modes. `--soft` moves the branch and leaves your staging area and files as they were. The default, `--mixed`, also resets the staging area to match that commit but keeps your files. `--hard` overwrites your tracked files too, discarding uncommitted changes to them. Untracked files are usually left alone, except where the target commit tracks a path that collides with an untracked file or folder.

Edits that were not staged or committed exist only in your working folder, so once `git restore` or `git reset --hard` overwrites them, Git cannot give them back.

Many newcomers believe that `git revert` deletes the bad commit. It does not. The original stays in the history and a second commit reverses it, so revert suits shared branches.

A common mistake is to run `git reset --hard` to undo a commit that teammates have already pulled. That rewrites your branch, so your next push is usually rejected unless you force it, and forcing it replaces history your teammates build on.
